# Verification helpers

The package uses component format 2. Installed helpers live under components/video-calls/verification; installed package.json/package-lock.json support `npm ci --prefix components/video-calls --ignore-scripts --no-audit --no-fund` in a private application copy.

## Provider entrypoints

`provider.mjs` exports `verifyMedia(context, dependencies): Promise<HelperResult>`. Dependencies are exactly `{Video,videoGrant,listRooms,createRoom,getRoom,deleteRoom,createClients,readSecrets,now}`. Production grant/client signatures remain unchanged. `adapters.mjs` exports `createProviderDependencies(context, {applicationClients} = {})` and `cleanupProvider(context)`.

createRoom accepts `{name:string,metadata:{aepmRunId:string}}` and resolves `{id:string,metadata:{aepmRunId:string}}`; getRoom(id:string) resolves that record or null; deleteRoom(id:string) resolves void. readSecrets resolves `{livekitKey:string,livekitSecret:string}`; now returns integer Unix milliseconds. createClients accepts `{room:string,publisherGrant,subscriberGrant,spectatorGrant}` with actual VideoGrant objects and resolves publisher/subscriber/spectator clients. Each client has asynchronous connect(), publishSynthetic(), disconnect(), reconnect(), enterDisplay(), close(), waitForFrames(minimum:number,timeoutMilliseconds:number):Promise<number>, attemptPublish():Promise<boolean>, and activeCaptureCount():Promise<number>. Client close stops media; caller-owned application pages are not closed by the component.

Optional code-owned applicationClients is `{pages,identities,applyGrants,enterDisplay,observe}`. Pages and identities have publisher/subscriber/spectator keys; identity values are `{id:string,name:string}`. All identities/pages must be distinct and prepared before grant generation. `applyGrants({room,publisherGrant,subscriberGrant,spectatorGrant}):Promise<void>` first binds the actual application Video through the page-local mediaVerification.bindVideo(actualVideo), then awaits recipe-owned intercepted real join responses. Binding rejects missing/invalid/replacement instances, preserves identity and disables real capture preferences without connecting. Initial connect waits for that same instance; it never bypasses the application join with a direct initial connection. `enterDisplay(role,page):Promise<void>` performs the actual application display transition. `observe(role,phase,page):Promise<void>` is awaited at connected/frames/display/closing. The recipe clears its application observations on error and supplies its own private-cards-hidden and participant-mapping assertions. Caller-owned pages/browsers remain caller-owned.

The shared driver uses actual Video, actual production grants and mapped publisher identity. Client cleanup invokes enterDisplay for application pages before closing media, preventing later application updates from reusing their grant. Existing exact loopback origins observed on prepared application pages are retained for local game traffic; no arbitrary external application origin is allowed. Provider service requests require exact paired socket/service origins and configured base paths; redirects fail. Account-wide ListRooms requires list-account-rooms. Creation requires a durable run intent; deletion also checks recorded identity and provider creation metadata. Result records contain no grants, credentials or raw provider output.

`provider-runner.mjs` runs the provider check; argument cleanup runs its cleanup hook. `prepare-provider.mjs` installs the full Chromium pinned by Playwright 1.64.1 only for local-provider/live modes, never for an in-memory fixture. Mode simulation/fixture uses fixture.mjs; synthetic frame counts there are simulated, not decoded live frames. Live/local-provider adapters use browser video frame callbacks. Neither a local fixture nor a local provider establishes deployed interoperability.

`browser-process.mjs` exports launchOwnedBrowser({profileRoot,timeoutMilliseconds?}), returning {browser,close}. It uses only the locked public chromium.executablePath(), with resolved executable/profile paths beneath runner-issued AEPM_PRIVATE_ROOT. Contextual profileRoot is the context directory's profiles/browser; standalone checks prepare their own private root. The fixed headless/fake-device/private-profile/mock-keychain flags do not bypass sandbox or permission checks. Chromium is spawned non-detached; connection uses the validated loopback DevToolsActivePort endpoint and supported connectOverCDP. Callers await owned.close(), which sends browser-level Browser.close, waits for the retained child and escalates within fixed deadlines. Transport disconnection is not process exit. Profiles remain for parent cleanup after containment is confirmed. This does not claim containment of arbitrary detached commands; actual runner interruption acceptance is separate from launcher fixtures.

## Native entrypoints

`native.py` exports read_context(), write_result(result), write_cleanup_result(result), environment(context), prepare_apple(context, *, project, scheme, derived_data, package_cache), run_apple(context, *, project, scheme, derived_data, package_cache, expected_targets, test_settings=None), prepare_android(context, *, project, tasks), run_android(context, *, project, tasks, artifact_paths), and cleanup_native(context). Paths and the expected target/type map are supplied by signed package/application code, not descriptor commands. Preparation does not accept expected_targets. Gradle preparation/execution uses shared prepare/run functions so validated Java selection and disabled automatic discovery/download stay enforced.

run_apple additionally accepts optional code-only test_settings. Keys are uppercase identifiers of at most 64 characters ending _TEST_SERVER_ADDRESS; values are HTTP loopback origins with explicit valid ports and no credentials, query, fragment, non-root path or control characters. Literal sorted NAME=value arguments precede fixed signing/action arguments. The caller supplies the same run-owned server address checked in its prepared test products; no descriptor or destination override is added.

Apple preparation requires an already generated and built test project. It creates a fresh private simulator set at the context directory's profiles/apple/runId and records creation before boot. The installer independently verifies that the prepared project discovers the recorded destination before main execution. run_apple uses only that recorded device, test-without-building and actual result-bundle counts. Cleanup is bounded and uses the private set plus recorded identity only. XcodeGen resolves its physical executable; package resolution uses explicit private checkout/cache paths with repository caching disabled.

Apple execution requires an exact nonempty mapping of at most 32 target names (at most 128 characters, no controls) to Unit test bundle or UI test bundle. Component MediaHost selects only MediaTests; MediaTelevision selects only MediaTelevisionTests, both unit bundles. The caller supplies its complete promised set; no type/name inference or aggregate fallback is allowed.

apple_results.py pins xcresulttool schema0.5.0, combines summary/tree queries within 30 seconds and 8 MiB, and limits trees to 100000 nodes/depth64. It matches each target/type exactly once and counts identified ordinary Test Case nodes, preferring nodeIdentifierURL over nodeIdentifier. Missing/unknown outcomes, duplicate identities, missing/wrong/duplicate targets, nested cases and ambiguous Arguments/Repetition/Test Case Run layouts fail. Diagnostic children are not execution counts. Each target needs non-skipped execution; the initial policy rejects failures and expected failures and reconciles all five summary counts. Sanitized per-target counts become a bound target-coverage artifact before aggregate assertions are emitted. Fixtures are labelled simulation; task-owned completed bundles are still required to establish real target-name/hierarchy acceptance. No unrelated application result is task execution evidence.

Android requires app/gradle.lockfile and gradle/verification-metadata.xml, strict checking and explicit validated Java resources. It uses runner-produced android-sdk-working/gradle-working beside the context file, never immutable seeds or user caches. Connected-test tasks create a fresh run-owned emulator with private profile/bridge-server state; unit tests require no device. Counts come from actual unit or instrumented test reports. Test doubles remain explicitly local simulation of media, not camera/provider evidence.

The Android bridge runs as an owned foreground server nodaemon child alongside the emulator, inheriting the runner's process group/job. Both handles are monitored, terminated and waited; either process disappearing fails the check. Client socket/address/port settings agree and use an explicit numeric loopback host to prevent automatic daemon startup on server loss. The foreground listener uses the supported localhost socket spelling. Cleanup only deletes recorded private files after process termination; it never starts or restarts a server.

## Result and ownership protocol

The installer supplies AEPM_CONTEXT_FILE with `{format,runId,package,id,mode,simulationKind,settings,resources,secrets,operations,origins,assertions}`, AEPM_RESULT_FILE, AEPM_OWNERSHIP_DIRECTORY and, when authorized, AEPM_SECRETS_FILE. Resource entries are `{id,path,digest}`. The secret file binds format/runId/package/id and values `{name:{version,value}}`; values stay in memory. These files are supplied by the trusted runner, not collected into application configuration.

Main result is `{format:1,runId,package,id,assertions,artifacts,resources,cleanup}`. Assertions are sorted `{id,passed,actual}`; actual is boolean, integer or null. Every declared assertion appears once, including unobserved false/null entries. Artifact records are `{path,digest,architecture}`. Owned resources are `{kind,id,namespace,createdByRunId,created,cleaned}`. Cleanup is `{required,attempted,completed,reason}`. Active helper processes leave final parent-owned completion pending; they do not attest their own process-tree termination.

The journal exclusively creates/flushed intent-counter.json before resource creation and created-counter.json afterward. Intent fields are `{format:1,runId,package,id,counter,kind,requestedId,namespace}`; created adds resourceId. Namespace is runId. Provider room names are ephemeralRoomPrefix-runId-counter, with creation metadata aepmRunId. Cleanup consumes these records only and emits `{format:1,runId,package,id,resources,cleanup}` to AEPM_CLEANUP_RESULT_FILE. No new creation authority is acquired during cleanup. The parent validates records, assertions, artifacts, containment and final profile removal.
